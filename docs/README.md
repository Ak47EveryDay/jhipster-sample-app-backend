# ドキュメント（jhipster-sample-app-backend）

このディレクトリには、リポジトリ `jhipster-sample-app-backend` の日本語の設計文書と規約文書を置く。
いずれもこのリポジトリの現在のコード（コミット `b4b3f74` 時点）を根拠に作成している。文書とコードが食い違う場合はコードを正とし、文書を修正すること。

## 構成

| ディレクトリ | 扱う内容 | 読む場面 |
| --- | --- | --- |
| [050_内部設計](./050_内部設計/README.md) | 内部設計書。アーキテクチャ、共通事項（設定、定数、権限、メッセージ、例外処理、セキュリティ、キャッシュ、ログと監視、メール、非同期処理）、機能別の処理と REST インタフェース、テーブル、リポジトリ、DB マイグレーション | 各機能の入出力や処理内容、テーブル定義、エラー応答を調べるとき |
| [999_標準化](./999_標準化/README.md) | 規約とシステム知識。プロジェクトの構成とレイヤー、共通部品、主要な処理フロー、命名・コーディング規約、REST とエンティティの追加手順、テストの作り方、ログと監視、設定とビルド、開発チェックリスト | 開発に着手するとき、書き方や手順を確認するとき |

## 読み方

1. まず [システム知識整理](./999_標準化/システム知識整理.md) で全体像をつかむ。
2. 開発に着手するときは [レイヤー別開発ガイド](./999_標準化/レイヤー別開発ガイド.md) と [ネーミング・コーディング規約](./999_標準化/ネーミング・コーディング規約.md) を読んでからコードを書く。機能を追加するときは [REST・エンティティ追加手順](./999_標準化/REST・エンティティ追加手順.md) に沿って進める。
3. 既存機能の入出力、処理内容、テーブル定義、エラー応答は [050_内部設計](./050_内部設計/README.md) で確認する。
4. 提出前に [開発チェックリスト](./999_標準化/開発チェックリスト.md) を確認する。

## 記載の約束

- 文書は日本語（常体）で書く。コードの識別子（クラス名、メソッド名、パス、設定キー）は原文のままバッククォートで囲む。
- 規則としては、このリポジトリのコード、テスト、ビルド設定から読み取れた事実だけを記載する。コードからは確定できない事項は「未確認」または「コードからの導出」として明示する。
- 各文書の冒頭に対象とするコミットを記す。コードや設定を変えたときは、対応する文書を更新する。
- フロントエンドの設計は別リポジトリ `jhipster-sample-app-frontend` にあり、このディレクトリには含めない。
- リポジトリルートの `README.md` は英語の概要（起動、ビルド、テスト）である。日本語での詳しい説明はこのディレクトリを参照すること。

## 用語の対応

設計文書（050_内部設計）と規約文書（999_標準化）は、それぞれ参照した文書の習慣に合わせて用語を選んでいる。次の語は表記が違うが、指すものは同じである。

| 概念 | 050_内部設計での表記 | 999_標準化での表記 |
| --- | --- | --- |
| REST のエンドポイントを定義するクラス | リソースクラス | REST コントローラ |
| コードに付ける注記（`@RestController` など） | アノテーション | 注釈 |
| アプリケーションの利用者 | ユーザ | ユーザー |
| HTTP のヘッダー | ヘッダ | ヘッダー |
| セキュリティのフィルターの連鎖 | フィルタチェイン | フィルターチェーン |
| リクエストとレスポンスの本文 | リクエスト本文 / 応答本文 | リクエストボディ / レスポンス |

パス変数、エンティティ、リポジトリ、DTO、サービスなどの表記は両者で同じである。
