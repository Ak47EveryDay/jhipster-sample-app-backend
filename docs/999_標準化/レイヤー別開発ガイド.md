# レイヤー別開発ガイド

> **位置づけ**：ソースのディレクトリ構成、パッケージ（レイヤー）ごとの担当、レイヤー間の依存方向の規則、各レイヤーの書き方を説明する。規則の根拠は、レイヤー間の依存を検証する ArchUnit のテスト（テストソースの `TechnicalStructureTest.java`）と既存コードである。
> パスは `src/main/java/io/github/jhipster/sample/` 基準で表記する。名前の付け方の詳細は `ネーミング・コーディング規約.md`、機能追加の手順は `REST・エンティティ追加手順.md` を参照。

---

## 2. パッケージとレイヤー

| パッケージ | 担当 | 主なクラス | ArchUnit 上のレイヤー |
|---|---|---|---|
| （ルート） | 起動 | `JhipsterSampleApplicationApp`、`ApplicationWebXml`、`GeneratedByJHipster` | レイヤー外 |
| `aop.logging` | ログ出力の AOP | `LoggingAspect` | レイヤー外 |
| `config` | Spring Boot の設定クラス群 | `SecurityConfiguration`、`LiquibaseConfiguration` など | `Config` |
| `domain` | JPA エンティティ | `User`、`Authority`、`BankAccount`、`Label`、`Operation`、`AbstractAuditingEntity` | `Domain` |
| `management` | 監視用のサービス | `SecurityMetersService` | レイヤー外 |
| `repository` | Spring Data JPA のリポジトリ | `*Repository`、`OperationRepositoryWithBagRelationships` とその実装 | `Persistence` |
| `security` | 認証・認可の支援クラス | `SecurityUtils`、`DomainUserDetailsService`、`AuthoritiesConstants` | `Security` |
| `service` | ビジネスロジック（ユーザー管理、メール）と業務例外 | `UserService`、`MailService` | `Service` |
| `service.dto` | サービスレイヤーの DTO | `AdminUserDTO`、`UserDTO`、`PasswordChangeDTO` | `Service` |
| `service.mapper` | エンティティと DTO の変換 | `UserMapper` | `Service` |
| `web.rest` | REST コントローラ | `*Resource`、`AuthenticateController` | `Web` |
| `web.rest.errors` | エラー応答 | `ExceptionTranslator`、`BadRequestAlertException` など | `Web` |
| `web.rest.vm` | REST エンドポイントの入力専用のオブジェクト（View Model。以下「VM」） | `LoginVM`、`ManagedUserVM`、`KeyAndPasswordVM` | `Web` |

- 本体の全パッケージに、一行の Javadoc を書いた `package-info.java` を置く（例：`domain/package-info.java` は `Domain objects.`）。
- 各レイヤーの担当は次のとおりである。
  - **`domain`**：テーブルに対応するエンティティと、その関連。永続化以外の処理は書かない。
  - **`repository`**：エンティティの検索と保存。Spring Data JPA のインターフェースとして定義する。
  - **`service`**：複数のリポジトリを組み合わせる処理、トランザクションの境界、メール送信、パスワードの照合。
  - **`web.rest`**：HTTP の入出力。パスの定義、入力チェック、ステータスコードとヘッダーの組み立て。
  - **`config`**：Spring Boot の Bean 定義。ほかのレイヤーから参照されない。
  - **`security`**：ログイン名の取得、`UserDetailsService` の実装、権限名の定数。

## 3. レイヤー間の依存方向の規則

### 3.1 規則の定義

依存方向はテストソースの `TechnicalStructureTest.java` が検証する。本体のクラスだけを対象にし（`DoNotIncludeTests`）、すべての種類の依存を調べる（`consideringAllDependencies()`）。規則は次の 1 つである。

```java
@ArchTest
static final ArchRule respectsTechnicalArchitectureLayers = layeredArchitecture()
    .consideringAllDependencies()
    .layer("Config").definedBy("..config..")
    .layer("Web").definedBy("..web..")
    .optionalLayer("Service").definedBy("..service..")
    .layer("Security").definedBy("..security..")
    .optionalLayer("Persistence").definedBy("..repository..")
    .layer("Domain").definedBy("..domain..")

    .whereLayer("Config").mayNotBeAccessedByAnyLayer()
    .whereLayer("Web").mayOnlyBeAccessedByLayers("Config")
    .whereLayer("Service").mayOnlyBeAccessedByLayers("Web", "Config")
    .whereLayer("Security").mayOnlyBeAccessedByLayers("Config", "Service", "Web")
    .whereLayer("Persistence").mayOnlyBeAccessedByLayers("Service", "Security", "Web", "Config")
    .whereLayer("Domain").mayOnlyBeAccessedByLayers("Persistence", "Service", "Security", "Web", "Config")

    .ignoreDependency(belongToAnyOf(JhipsterSampleApplicationApp.class), alwaysTrue())
    .ignoreDependency(alwaysTrue(), belongToAnyOf(
        io.github.jhipster.sample.config.Constants.class,
        io.github.jhipster.sample.config.ApplicationProperties.class
    ));
```

### 3.2 読み方

「依存される側」から見て、依存してよいレイヤーは次のとおりである。

| 依存される側 | 依存してよいレイヤー | 本体のコードでの例 |
|---|---|---|
| `config` | なし | なし |
| `web` | `config` | `config` から `web` を使う箇所は現状ない。同じレイヤー内では `web.rest.AccountResource` が `web.rest.vm.*` を使う |
| `service` | `web`、`config` | `web.rest.UserResource` が `service.UserService` を使う |
| `security` | `config`、`service`、`web` | `service.UserService` が `security.SecurityUtils` を使う |
| `repository` | `service`、`security`、`web`、`config` | `security.DomainUserDetailsService` が `repository.UserRepository` を使う |
| `domain` | `persistence`、`service`、`security`、`web`、`config` | `repository.UserRepository` が `domain.User` を使う |

「依存する側」からまとめると、次のようになる。

```
config     ──▶ ほかのレイヤーを参照できる（参照されることはない）
web        ──▶ service, security, repository, domain
service    ──▶ security, repository, domain
security   ──▶ repository, domain
repository ──▶ domain
domain     ──▶ ほかのレイヤーを参照しない（config.Constants と config.ApplicationProperties のみ例外）
```

- 同じレイヤー内のクラスを参照している箇所もある（例：`service.UserService` から `service.dto.AdminUserDTO`、`web.rest.AccountResource` から `web.rest.errors.*`）。
- `config.Constants` と `config.ApplicationProperties` だけは、どのレイヤーからも参照してよい（`ignoreDependency` の指定による）。例：`domain.User` が `config.Constants.LOGIN_REGEX` を使う。
- 起動クラス `JhipsterSampleApplicationApp` からの依存は、すべて規則の対象外である。
- `aop.logging`、`management`、ルートのパッケージはどのレイヤーにも属さない。`config.SecurityJwtConfiguration` は `management.SecurityMetersService` を参照している。

### 3.3 開発上の意味

| してはいけないこと | 理由 | 代わりの方法 |
|---|---|---|
| `service` から `web.rest` のクラスを使う | `Web` にアクセスできるのは `Config` のみ | 業務例外は `service` パッケージに置く（`service.EmailAlreadyUsedException` など）。エラー応答への変換は `web.rest.errors.ExceptionTranslator` が行う |
| `domain` や `repository` から `service`、`security`、`web` を使う | `Domain` と `Persistence` にアクセスできるレイヤーに含まれない | 関連する処理を呼び出す側（`service` または `web.rest`）に置く |
| `config` のクラスを `config` 以外から参照する | `Config` はどのレイヤーからもアクセスできない。規則の対象外は、起動クラス `JhipsterSampleApplicationApp` からの依存と、`Constants` と `ApplicationProperties` への依存だけである | 定数は `config.Constants`、設定値は `config.ApplicationProperties` に置く |
| 新しいパッケージを追加する | 既存のレイヤーに属さないパッケージ（`aop.logging`、`management` など）は `definedBy` の指定に含まれない。既存のコードでは、これらのパッケージから `config` を参照している箇所はない | 既存のレイヤーに収まるパッケージ名にする。レイヤーの定義を変える場合は `TechnicalStructureTest` の `definedBy` を更新する |

## 4. `domain`（エンティティ）

最も単純な `domain/Label.java` を見本にする。

```java
@Entity
@Table(name = "label")
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
@SuppressWarnings("common-java:DuplicatedBlocks")
public class Label implements Serializable {

    @Serial
    private static final long serialVersionUID = 1L;

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "sequenceGenerator")
    @SequenceGenerator(name = "sequenceGenerator")
    @Column(name = "id")
    private Long id;

    @NotNull
    @Size(min = 3)
    @Column(name = "label", nullable = false)
    private String label;

    @ManyToMany(fetch = FetchType.LAZY, mappedBy = "labels")
    @Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
    @JsonIgnoreProperties(value = { "bankAccount", "labels" }, allowSetters = true)
    private Set<Operation> operations = new HashSet<>();

    // jhipster-needle-entity-add-field - JHipster will add fields here

    // （中略: getter と setter）

    public Label label(String label) {       // 自身を返すセッター（メソッドチェーンで値を設定するため）
        this.setLabel(label);
        return this;
    }

    public Label addOperation(Operation operation) {   // 関連の両側をそろえる
        this.operations.add(operation);
        operation.getLabels().add(this);
        return this;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) {
            return true;
        }
        if (!(o instanceof Label)) {
            return false;
        }
        return getId() != null && getId().equals(((Label) o).getId());
    }

    @Override
    public int hashCode() {
        // see https://vladmihalcea.com/how-to-implement-equals-and-hashcode-using-the-jpa-entity-identifier/
        return getClass().hashCode();
    }

    // prettier-ignore
    @Override
    public String toString() {
        return "Label{" +
            "id=" + getId() +
            ", label='" + getLabel() + "'" +
            "}";
    }
}
```

| 規則・作法 | 内容 | 根拠 |
|---|---|---|
| クラスの注釈 | `@Entity`、`@Table(name = "<テーブル名>")`、`@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)` を付ける。`implements Serializable` と `@Serial private static final long serialVersionUID = 1L;` を書く | `domain/Label.java`、`domain/BankAccount.java`、`domain/Operation.java` |
| 主キー | `Long id`。`@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "sequenceGenerator")` と `@SequenceGenerator(name = "sequenceGenerator")` を付ける | 同上 |
| カラム | `@Column(name = "<スネークケースのカラム名>")` を付ける。`nullable`、`length`、`precision`、`scale` はチェンジログの定義にそろえる | `domain/User.java`（`length = 50` など）、`domain/BankAccount.java`（`precision = 21, scale = 2`） |
| 入力チェック | フィールドに Bean Validation の注釈を付ける。使っているのは `@NotNull`、`@Size`、`@Pattern`、`@Email` | `domain/User.java`、`domain/Label.java` |
| 関連 | `fetch = FetchType.LAZY` を指定する。多対 1 は `@ManyToOne`、逆方向の 1 対多は `@OneToMany(mappedBy = ...)`、多対多は `@ManyToMany` と `@JoinTable` を使う | `domain/Operation.java` |
| JSON の循環回避 | 関連のフィールドに `@JsonIgnoreProperties` を付け、双方向の参照で相手側のフィールドを除外する | `domain/BankAccount.java` の `operations` |
| セッター | 通常の `setXxx` のほかに、`xxx(値)` の形で自身を返すメソッドを持つ | `domain/BankAccount.java` の `name(String)`、`balance(BigDecimal)` |
| 関連の追加・削除 | `addXxx`、`removeXxx` を用意し、両側の参照をそろえる | `domain/Label.java` の `addOperation`、`removeOperation` |
| `equals` と `hashCode` | `equals` は id が等しいかどうかで判定する。`hashCode` は `getClass().hashCode()` を返す。`Authority` だけは `name`（主キー）で比較し、`hashCode` は `Objects.hashCode(getName())` を返す | `domain/Label.java`、`domain/BankAccount.java`、`domain/Operation.java`、`domain/User.java`（例外は `domain/Authority.java`） |
| `toString` | `// prettier-ignore` を付ける。パスワードなどの機微な項目は含めない | `domain/User.java`、`web/rest/vm/LoginVM.java` |
| 監査項目 | 作成者・作成日時・更新者・更新日時を持つエンティティは `AbstractAuditingEntity` を継承する。現状は `User` のみ | `domain/AbstractAuditingEntity.java` |
| 警告の抑制 | `@SuppressWarnings("common-java:DuplicatedBlocks")` をクラスに付ける（`BankAccount`、`Label`、`Operation`、`Authority`。`User` には付いていない） | `domain/BankAccount.java`、`domain/Label.java`、`domain/Operation.java`、`domain/Authority.java` |

- `Authority` は `name` を主キーにするため `Persistable<String>` を実装し、`isNew()` の判定に `isPersisted` フラグを使っている（`domain/Authority.java`）。
- `User.setLogin` は保存前にログイン名を小文字に変換している。
- エンティティに `// jhipster-needle-entity-add-field` などのコメント（`jhipster-needle-...`）が残っている。これは JHipster のジェネレーターがコードを挿入する位置を示す印である。本リポジトリは再生成できないが、コメントはそのまま残されている。

## 5. `repository`（リポジトリ）

`repository/BankAccountRepository.java` の抜粋を示す。

```java
@Repository
public interface BankAccountRepository extends JpaRepository<BankAccount, Long> {
    @Query("select bankAccount from BankAccount bankAccount where bankAccount.user.login = ?#{authentication.name}")
    List<BankAccount> findByUserIsCurrentUser();

    default Optional<BankAccount> findOneWithEagerRelationships(Long id) {
        return this.findOneWithToOneRelationships(id);
    }

    @Query(
        value = "select bankAccount from BankAccount bankAccount left join fetch bankAccount.user",
        countQuery = "select count(bankAccount) from BankAccount bankAccount"
    )
    Page<BankAccount> findAllWithToOneRelationships(Pageable pageable);

    @Query("select bankAccount from BankAccount bankAccount left join fetch bankAccount.user where bankAccount.id =:id")
    Optional<BankAccount> findOneWithToOneRelationships(@Param("id") Long id);
}
```

| 規則・作法 | 内容 | 根拠 |
|---|---|---|
| 定義の形 | `@Repository` を付けたインターフェースで、`JpaRepository<エンティティ, 主キーの型>` を継承する。実装クラスは書かない | `repository/*Repository.java` |
| 検索メソッド | 単純な条件はメソッド名から導出する（`findOneByLogin`、`findAllByActivatedIsFalseAndActivationKeyIsNotNullAndCreatedDateBefore`）。複雑な場合は `@Query` に JPQL を書く | `repository/UserRepository.java` |
| 関連の取得 | `@OneToMany` と `@ManyToMany` は遅延読み込みで、OSIV は無効（`spring.jpa.open-in-view: false`）。レスポンスに含める関連は、`left join fetch` を使った `findAllWithEagerRelationships`、`findOneWithEagerRelationships` で取得する | `repository/BankAccountRepository.java`、`repository/OperationRepository.java` |
| ページング | ページを返す `@Query` には `countQuery` を併記する | `repository/BankAccountRepository.java` |
| 複数のコレクションを取得する場合 | `join fetch` を 1 クエリにまとめず、`<リポジトリ名>WithBagRelationships` というフラグメント・インターフェースと、その実装 `<リポジトリ名>WithBagRelationshipsImpl`（`EntityManager` を使う）で別クエリとして読み込む | `repository/OperationRepositoryWithBagRelationships.java`、`repository/OperationRepositoryWithBagRelationshipsImpl.java` |
| キャッシュ | ユーザーの検索は `@Cacheable(cacheNames = ..., unless = "#result == null")` を付け、`@EntityGraph(attributePaths = "authorities")` で権限も一緒に読む | `repository/UserRepository.java` |
| 名前付きパラメーター | `@Query` 内の `:名前` には `@Param` を付ける | `repository/BankAccountRepository.java` |
| 中身が空のリポジトリ | `@SuppressWarnings("unused")` を付ける | `repository/AuthorityRepository.java`、`repository/LabelRepository.java` |

- `BankAccountRepository.findByUserIsCurrentUser` は定義されているが、本リポジトリには呼び出し元がない。
- キャッシュ領域は `config/CacheConfiguration.java` の `cacheManagerCustomizer` にエンティティごとに登録する。`@Cache` を付けたエンティティを追加するときは、そこにも登録を追加する。

## 6. `service`、`service.dto`、`service.mapper`

### 6.1 サービス

```java
@Service
@Transactional
public class UserService {

    private static final Logger LOG = LoggerFactory.getLogger(UserService.class);

    private final UserRepository userRepository;
    // （ほかの依存は省略）

    public UserService(UserRepository userRepository, /* ... */) {
        this.userRepository = userRepository;
    }

    @Transactional(readOnly = true)
    public Page<AdminUserDTO> getAllManagedUsers(Pageable pageable) {
        return userRepository.findAll(pageable).map(AdminUserDTO::new);
    }
}
```

| 規則・作法 | 内容 | 根拠 |
|---|---|---|
| 定義の形 | `@Service` を付けた具象クラス。インターフェースは定義しない | `service/UserService.java`、`service/MailService.java` |
| 依存の受け取り | コンストラクタ注入。フィールドは `private final` にする | `service/UserService.java`、`service/MailService.java` |
| トランザクション | DB を扱うサービスは、クラスに `@Transactional` を付け、参照のみのメソッドには `@Transactional(readOnly = true)` を付ける。DB を扱わない `MailService` には付けていない | `service/UserService.java`、`service/MailService.java` |
| 業務例外 | `RuntimeException` を継承した例外クラスを `service` パッケージに置き、投げる | `service/UsernameAlreadyUsedException.java` など |
| キャッシュの整理 | ユーザーを保存・削除したあとに `clearUserCaches(user)` を呼ぶ | `service/UserService.java` |
| 非同期処理 | 非同期で実行する公開メソッドに `@Async` を付ける。実際の処理は `private` の同期メソッドに分ける | `service/MailService.java` の `sendEmail` と `sendEmailSync` |
| 定期実行 | `@Scheduled(cron = "0 0 1 * * ?")` を付ける | `service/UserService.java` の `removeNotActivatedUsers` |

- 口座・ラベル・取引の 3 エンティティにはサービスクラスがない。REST コントローラがリポジトリを直接呼び、トランザクションは REST コントローラのクラス単位の `@Transactional(rollbackFor = Exception.class)` で確保している。
- `service` の例外と `web.rest.errors` の例外は、対応するものどうしで名前が同じとは限らない。`EmailAlreadyUsedException` と `InvalidPasswordException` は同名の例外が `web.rest.errors` にもあり、`service.UsernameAlreadyUsedException` には `web.rest.errors.LoginAlreadyUsedException` が対応する。これらは別のクラスであり、`web.rest.errors.ExceptionTranslator` が `service` 側を `web.rest.errors` 側のエラー応答に変換する。`import` するときはパッケージに注意すること。

### 6.2 DTO

| 種類 | 置き場所 | 役割 | 例 |
|---|---|---|---|
| DTO | `service.dto` | サービスレイヤーと REST レイヤーの間で受け渡すオブジェクト | `AdminUserDTO`、`UserDTO`、`PasswordChangeDTO` |
| VM | `web.rest.vm` | 特定の REST エンドポイントの入力専用のオブジェクト | `LoginVM`、`ManagedUserVM`、`KeyAndPasswordVM` |

DTO の作法（`service/dto/AdminUserDTO.java`）は次のとおりである。

- `implements Serializable` と `serialVersionUID` を書く。
- Jackson のために引数なしのコンストラクタを用意する（コメントは `Empty constructor needed for Jackson.`）。
- エンティティを引数に取るコンストラクタを持つ（`new AdminUserDTO(user)`）。
- 入力として使う項目には Bean Validation の注釈を付ける（`@NotBlank`、`@Pattern`、`@Size`、`@Email`）。
- getter と setter、`toString` を書く。

口座・ラベル・取引のエンドポイントは DTO を使わず、エンティティをそのままリクエストボディ・レスポンスボディにする。DTO を使うのはユーザーだけである。`Authority` もエンティティをそのままリクエストボディ・レスポンスボディにし、`AuthorityResource` がリポジトリを直接呼ぶ。

### 6.3 マッパー

`service/mapper/UserMapper.java` はエンティティ `User` と DTO の変換を手書きしたクラスである（`@Service`）。MapStruct の `@Named`、`@BeanMapping`、`@Mapping` をメソッドに付けているが、クラスに `@Mapper` は付いていない。本コード内に `UserMapper` を使う箇所は現状なく、テストソースの `service/mapper/UserMapperTest.java` で検証している。

## 7. `web.rest`（REST コントローラ）

`web/rest/LabelResource.java` を見本にする。

```java
@RestController
@RequestMapping("/api/labels")
@Transactional(rollbackFor = Exception.class)
public class LabelResource {

    private static final Logger LOG = LoggerFactory.getLogger(LabelResource.class);

    private static final String ENTITY_NAME = "label";

    @Value("${jhipster.clientApp.name:jhipsterSampleApplication}")
    private String applicationName;

    private final LabelRepository labelRepository;

    public LabelResource(LabelRepository labelRepository) {
        this.labelRepository = labelRepository;
    }

    /**
     * {@code POST  /labels} : Create a new label.
     * （引数・戻り値・例外の説明）
     */
    @PostMapping("")
    public ResponseEntity<Label> createLabel(@Valid @RequestBody Label label) throws URISyntaxException {
        LOG.debug("REST request to save Label : {}", label);
        if (label.getId() != null) {
            throw new BadRequestAlertException("A new label cannot already have an ID", ENTITY_NAME, "idexists");
        }
        label = labelRepository.save(label);
        return ResponseEntity.created(new URI("/api/labels/" + label.getId()))
            .headers(HeaderUtil.createEntityCreationAlert(applicationName, true, ENTITY_NAME, label.getId().toString()))
            .body(label);
    }
}
```

### 7.1 エンティティ向け REST コントローラのメソッド構成

`BankAccount`、`Label`、`Operation` の 3 クラスは同じ構成を持つ。

| 処理 | マッピング | メソッド名 | 成功時のレスポンス | 主なチェック |
|---|---|---|---|---|
| 作成 | `@PostMapping("")` | `create<Entity>` | `201`、`Location` ヘッダー、作成通知のアラートヘッダー | id がないこと（`idexists`） |
| 更新 | `@PutMapping("/{id}")` | `update<Entity>` | `200`、更新通知のアラートヘッダー | リクエストボディに id があること（`idnull`）、パスとリクエストボディの id が一致すること（`idinvalid`）、対象が存在すること（`idnotfound`） |
| 部分更新 | `@PatchMapping(value = "/{id}", consumes = { "application/json", "application/merge-patch+json" })` | `partialUpdate<Entity>` | `200`、更新通知のアラートヘッダー | 更新と同じ |
| 一覧 | `@GetMapping("")` | `getAll<Entity>s` | `200`（`Operation` はページングのヘッダーを伴う） | なし |
| 取得 | `@GetMapping("/{id}")` | `get<Entity>` | `200`。なければ `404` | なし |
| 削除 | `@DeleteMapping("/{id}")` | `delete<Entity>` | `204`、削除通知のアラートヘッダー | なし |

### 7.2 作法

| 規則・作法 | 内容 | 根拠 |
|---|---|---|
| パス | `/api/<リソース名>`。リソース名はケバブケースの複数形（`/api/bank-accounts`） | `web/rest/*Resource.java` の `@RequestMapping` |
| トランザクション | クラスに `@Transactional(rollbackFor = Exception.class)` を付ける（エンティティ向けの 4 コントローラすべてに付いている。`UserService` を経由する `AccountResource`、`UserResource` には付いていない） | `web/rest/BankAccountResource.java` など |
| 定数 | `LOG`、`ENTITY_NAME`（小文字で始まるエンティティ名）、`applicationName`（`@Value("${jhipster.clientApp.name:jhipsterSampleApplication}")`）を宣言する | 同上 |
| Javadoc | `{@code POST  /labels} : Create a new label.` の書式で、HTTP メソッド、パス、目的を書く | 各コントローラメソッド |
| ログ | メソッドの先頭で `LOG.debug("REST request to ...")` を出す | 各コントローラメソッド |
| 入力チェック | 作成と更新は `@Valid @RequestBody` を付ける。部分更新は `@NotNull @RequestBody` を付ける（`@Valid` は付けない。null の項目は `updateIfPresent` により更新対象外になる） | `web/rest/BankAccountResource.java` |
| 部分更新 | 既存のエンティティを読み込み、null でない項目だけを `updateIfPresent(setter, value)` で設定する | 同上の `partialUpdateBankAccount` |
| 404 | `ResponseUtil.wrapOrNotFound(Optional)` を使う | `getBankAccount` |
| アラートヘッダー | `HeaderUtil.createEntityCreationAlert`、`createEntityUpdateAlert`、`createEntityDeletionAlert` を `ResponseEntity` の `headers` に設定する | 各メソッド |
| ページング | 引数に `@org.springdoc.core.annotations.ParameterObject Pageable pageable` を取り、`PaginationUtil.generatePaginationHttpHeaders(ServletUriComponentsBuilder.fromCurrentRequest(), page)` でヘッダーを組み立てる | `web/rest/OperationResource.java`、`web/rest/UserResource.java` |
| ソート対象の制限 | ユーザーの一覧は `ALLOWED_ORDERED_PROPERTIES` に含まれるプロパティだけをソートに許し、それ以外は `400` を返す | `web/rest/UserResource.java`、`web/rest/PublicUserResource.java` |
| 管理者限定 | メソッドに `@PreAuthorize` を付ける | `web/rest/UserResource.java`、`web/rest/AuthorityResource.java` |

- 一覧取得の `eagerload` パラメーターの既定値は `true` で、`false` のときは関連を読まずに返す（`getAllBankAccounts`、`getAllOperations`）。
- 更新・部分更新で対象が存在しない場合は `404` ではなく `400`（`idnotfound`）を返す。`404` を返すのは取得の `get<Entity>` だけである。

## 8. `web.rest.errors`（エラー応答）

`@ControllerAdvice` の `ExceptionTranslator` が、コントローラから送出された例外を RFC 7807 形式のレスポンス（メディアタイプ `application/problem+json`）に変換する。テストではレスポンスのメディアタイプを `MediaType.APPLICATION_PROBLEM_JSON` で検証している。REST コントローラが使うのは主に `BadRequestAlertException` である。詳細は `主要処理フロー.md` の「エラーからエラー応答まで」と `モジュール構成と共通部品.md` を参照。

## 10. レイヤーをまたぐ作法

| 項目 | 作法 | 根拠 |
|---|---|---|
| 依存の受け取り | コンストラクタ注入。`@Autowired` を使うのは `config/CacheKeyGeneratorConfiguration.java` のセッターメソッド（`@Autowired(required = false)`）だけである | 本体全ソース |
| ロガー | `private static final Logger LOG = LoggerFactory.getLogger(<クラス>.class);` を宣言する | 本体全ソース |
| ユーティリティクラス | `final` なクラスにし、`private` のコンストラクタを宣言する | `config/Constants.java`、`security/SecurityUtils.java`、`web/rest/errors/ErrorConstants.java` |
| Lombok | 使わない。getter と setter は手書き | `pom.xml` に依存がない |
| `record` | 使わない。DTO と VM はクラスとして定義する | 本体全ソース |
| 書式 | Java は 4 スペースのインデント、UTF-8、LF、末尾に改行 | `.editorconfig` |
| コメント | クラスと公開メソッドに Javadoc を書く（英語）。`toString` の手書きの連結には `// prettier-ignore` を付ける | 各クラス |
