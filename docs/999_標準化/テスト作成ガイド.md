# テスト作成ガイド

> **位置づけ**：本リポジトリのテストがどう分類され、どう実行され、どこに置かれ、どう書かれているかをまとめたものである。実行コマンドとビルドの設定は `設定とビルド手順.md` を参照。
> パスは `src/test/java/io/github/jhipster/sample/` 基準（テストソース）で表記する。Gatling のシミュレーションだけは `src/test/java/gatling/simulations/` 基準である。

---

## 1. テストの種類と実行のされ方

| 種類 | 対象のクラス | 実行するプラグイン | Spring のコンテキスト | クラス数 |
|---|---|---|---|---|
| 単体テスト | クラス名に `IT` を含まないテストクラス | `maven-surefire-plugin`（`test` フェーズ） | 使わない | 11 |
| 統合テスト | `**/*IT*`、`**/*IntTest*` に一致するクラス | `maven-failsafe-plugin`（`integration-test` と `verify` のフェーズ） | 使う | 16 |
| 負荷試験 | `gatling.simulations.<エンティティ>GatlingTest` | `gatling-maven-plugin`（ライフサイクルには結びついていない） | 使わない | 3 |

- クラス名に `IT` を含むクラスは surefire から除外され、failsafe が実行する（`pom.xml` の両プラグインの `<includes>` と `<excludes>`）。したがって補助クラスの名前に `IT` を含めないこと。
- failsafe は `-Dspring.profiles.active=${profile.test}` を付けて実行する。既定（Maven プロファイル `dev`）は `test,testdev`、`-Pprod` のときは `test,testprod` である。
- `./mvnw test` の段階では統合テストは実行されない。`./mvnw verify` で単体テスト、統合テスト、パッケージ化までが実行される。
- CI は `./mvnw -ntp --batch-mode -Pprod verify` を実行する（`.github/workflows/github-actions.yml`）。統合テストは PostgreSQL のコンテナーで動く。
- 単体テストと統合テストの両方で JaCoCo によるカバレッジを計測する（`pom.xml` の `jacoco-maven-plugin`）。

## 2. ファイルの命名と置き場所

テストは本体と同じパッケージ構成にし、テスト対象のクラスと同じパッケージに置く。

| 種類 | 命名 | 例 | 置き場所 |
|---|---|---|---|
| 単体テスト | `<対象クラス>Test` | `BankAccountTest`、`WebConfigurerTest`、`UserMapperTest` | 対象と同じパッケージ |
| 単体テスト（別の書き方をしているもの） | `<対象クラス>Tests`、`<対象クラス>UnitTest` | `SecurityMetersServiceTests`、`SecurityUtilsUnitTest` | 同上 |
| 統合テスト | `<対象クラス>IT` | `BankAccountResourceIT`、`UserServiceIT` | 同上 |
| エンティティのサンプルを生成する | `<エンティティ>TestSamples` | `BankAccountTestSamples` | `domain` |
| エンティティを検証する | `<エンティティ>Asserts` | `BankAccountAsserts` | `domain` |
| 検証に使う比較器 | `AssertUtils` | `AssertUtils` | `domain` |
| REST のテストの共通部品 | `TestUtil` | `TestUtil` | `web/rest` |
| 認証状態を作る注釈 | `WithUnauthenticatedMockUser` | `WithUnauthenticatedMockUser` | `web/rest` |
| JWT を作る道具 | `JwtAuthenticationTestUtils` | `JwtAuthenticationTestUtils` | `security/jwt` |
| 統合テスト用の合成注釈 | `IntegrationTest`、`AuthenticationIntegrationTest` | 同左 | ルート、`security/jwt` |
| テスト用の設定 | `AsyncSyncConfiguration` | `AsyncSyncConfiguration` | `config` |
| テスト用の DB コンテナー関係 | `DatabaseTestcontainer`、`SqlTestContainer`、`EmbeddedSQL`、`SqlTestContainersSpringContextCustomizerFactory` | 同左 | `config` |
| テストの実行順序 | `SpringBootTestClassOrderer` | `SpringBootTestClassOrderer` | `config` |
| テスト専用のコントローラ | `<目的>TestController` | `WebConfigurerTestController`、`ExceptionTranslatorTestController` | `config`、`web/rest/errors` |
| テスト専用のエンティティ | `DateTimeWrapper`、`DateTimeWrapperRepository` | 同左 | `repository/timezone` |
| 負荷試験 | `<エンティティ>GatlingTest` | `BankAccountGatlingTest` | `src/test/java/gatling/simulations/` |

- 単体テストの名前は `<対象クラス>Test` が基本で、`Tests` や `UnitTest` で終わるクラスが 1 つずつある。新しい単体テストは `<対象クラス>Test` に合わせるのがよい。
- テスト専用のコントローラは `@RestController` を付けたテストソースのクラスである。`@IntegrationTest` が本体の起動クラスを読み込むため、テストのコンテキストに一緒に登録される。
- `src/test/resources/` にはテスト用の設定（`config/`）、`logback.xml`、`junit-platform.properties`、`META-INF/spring.factories`、メールのテンプレートとメッセージがある。

## 3. 統合テストの基本形

### 3.1 クラスに付ける注釈

```java
@IntegrationTest
@AutoConfigureMockMvc
@WithMockUser
class BankAccountResourceIT {

    @Autowired
    private MockMvc restBankAccountMockMvc;
```

| 注釈 | 役割 | 備考 |
|---|---|---|
| `@IntegrationTest` | 合成注釈。`@SpringBootTest` に読み込むクラスを指定したものと、`@EmbeddedSQL` を組み合わせる | 定義は `IntegrationTest.java` |
| `@AutoConfigureMockMvc` | `MockMvc` を使えるようにする | `org.springframework.boot.webmvc.test.autoconfigure` |
| `@WithMockUser` | 認証済みの状態を作る。クラスにもメソッドにも付けられる | 管理者権限が必要なときは `@WithMockUser(authorities = AuthoritiesConstants.ADMIN)` |
| `@WithUnauthenticatedMockUser` | 未認証の状態を作る | 定義は `web/rest/WithUnauthenticatedMockUser.java` |
| `@Transactional` | テストメソッド（またはクラス）の終了時に DB の変更を戻す | DB を変更するメソッドに付ける |
| `@MockitoBean` | Spring の Bean を Mockito のモックに置き換える | `UserServiceIT` の `DateTimeProvider`、`MailServiceIT` の `JavaMailSender` |
| `@ExtendWith(MockitoExtension.class)` と `@Mock` | Spring に登録しないモックを使う | `BankAccountResourceIT`、`OperationResourceIT`、`MailServiceIT` |

`IntegrationTest` の定義は次のとおりである。

```java
@SpringBootTest(
    classes = {
        JhipsterSampleApplicationApp.class,
        AsyncSyncConfiguration.class,
        io.github.jhipster.sample.config.JacksonHibernateConfiguration.class,
    }
)
@EmbeddedSQL
public @interface IntegrationTest {}
```

- `@WithMockUser` は認証済みの状態を作るだけである。JWT の検証そのものを試すテストは 7 節を参照。
- `@Transactional` を付けていないテストは、`@AfterEach` で登録したデータを削除する（`BankAccountResourceIT#cleanup`、`AccountResourceIT#checkUsers` など）。

### 3.2 REST コントローラの統合テストの構成

`web/rest/BankAccountResourceIT.java` を見本にする。

| 要素 | 内容 |
|---|---|
| 定数 | `DEFAULT_<項目>`、`UPDATED_<項目>`（文字列は `"AAAAAAAAAA"`、`"BBBBBBBBBB"`）。`ENTITY_API_URL`（`"/api/bank-accounts"`）、`ENTITY_API_URL_ID`（`ENTITY_API_URL + "/{id}"`） |
| フィールド | `om`（`tools.jackson.databind.ObjectMapper`）、対象のリポジトリ、`em`（`EntityManager`）、`rest<エンティティ>MockMvc` |
| `createEntity()`、`createUpdatedEntity()` | テスト対象のエンティティを作る `static` メソッド。ほかのエンティティのテストからも呼べるようにするためである |
| `@BeforeEach initTest()` | エンティティを組み立てる |
| `@AfterEach cleanup()` | 挿入したエンティティを削除する |
| 件数の検証 | `getRepositoryCount()` と、`assertIncrementedRepositoryCount`、`assertDecrementedRepositoryCount`、`assertSameRepositoryCount` |
| 保存結果の検証 | `getPersistedBankAccount` で読み直し、`BankAccountAsserts` の `assertBankAccountUpdatableFieldsEquals` などで比べる |

```java
@Test
@Transactional
void createBankAccount() throws Exception {
    long databaseSizeBeforeCreate = getRepositoryCount();
    // Create the BankAccount
    var returnedBankAccount = om.readValue(
        restBankAccountMockMvc
            .perform(post(ENTITY_API_URL).contentType(MediaType.APPLICATION_JSON).content(om.writeValueAsBytes(bankAccount)))
            .andExpect(status().isCreated())
            .andReturn()
            .getResponse()
            .getContentAsString(),
        BankAccount.class
    );

    // Validate the BankAccount in the database
    assertIncrementedRepositoryCount(databaseSizeBeforeCreate);
    assertBankAccountUpdatableFieldsEquals(returnedBankAccount, getPersistedBankAccount(returnedBankAccount));

    insertedBankAccount = returnedBankAccount;
}

@Test
@Transactional
void getNonExistingBankAccount() throws Exception {
    // Get the bankAccount
    restBankAccountMockMvc.perform(get(ENTITY_API_URL_ID, Long.MAX_VALUE)).andExpect(status().isNotFound());
}
```

### 3.3 エンティティ向け REST コントローラに用意されているテストケース

| 処理 | テストメソッド（`BankAccount` の場合） | 確認すること |
|---|---|---|
| 作成 | `createBankAccount` | `201`、件数が 1 件増える、保存された値が一致する |
| 作成（id 指定あり） | `createBankAccountWithExistingId` | `400`、件数が変わらない |
| 必須項目 | `checkNameIsRequired`、`checkBalanceIsRequired` | `400`、件数が変わらない |
| 一覧 | `getAllBankAccounts` | `200`、JSON に作成した値が含まれる |
| 取得 | `getBankAccount`、`getNonExistingBankAccount` | `200`、`404` |
| 更新 | `putExistingBankAccount` | `200`、保存された値が一致する |
| 更新の失敗 | `putNonExistingBankAccount`、`putWithIdMismatchBankAccount`、`putWithMissingIdPathParamBankAccount` | `400`、`400`、`405` |
| 部分更新 | `partialUpdateBankAccountWithPatch`、`fullUpdateBankAccountWithPatch` | `200`、指定した項目だけが更新される |
| 部分更新の失敗 | `patchNonExistingBankAccount`、`patchWithIdMismatchBankAccount`、`patchWithMissingIdPathParamBankAccount` | `400`、`400`、`405` |
| 削除 | `deleteBankAccount` | `204`、件数が 1 件減る |

- 更新のテストでは、読み込んだエンティティを `em.detach(...)` でセッションから切り離してから値を変えている（`putExistingBankAccount`）。
- 部分更新は `contentType("application/merge-patch+json")` で送り、期待値は `TestUtil.createUpdateProxyForBean(partialUpdated, original)` で作る。
- レスポンスの JSON は `jsonPath(...)` と Hamcrest のマッチャー（`hasItem`、`TestUtil.sameNumber`）で検証する。

## 4. エンティティのテスト（三点セット）

エンティティごとに `<エンティティ>Test`、`<エンティティ>TestSamples`、`<エンティティ>Asserts` の 3 ファイルを `domain` に置く。`Label` が最も単純な見本である。

| ファイル | 役目 | メソッド |
|---|---|---|
| `<エンティティ>Test` | `equals` と、関連を追加・削除したときの両側の状態を検証する。Spring のコンテキストは使わない | `equalsVerifier`（`TestUtil.equalsVerifier(<エンティティ>.class)` を呼ぶ）、関連ごとのテスト（`operationTest` など） |
| `<エンティティ>TestSamples` | サンプルのエンティティを返す `static` メソッド | `get<エンティティ>Sample1()`、`get<エンティティ>Sample2()`、`get<エンティティ>RandomSampleGenerator()` |
| `<エンティティ>Asserts` | エンティティ同士を比べる `static` メソッド | `assert<エンティティ>AllPropertiesEquals`、`assert<エンティティ>AllUpdatablePropertiesEquals`、`assert<エンティティ>AutoGeneratedPropertiesEquals`、`assert<エンティティ>UpdatableFieldsEquals`、`assert<エンティティ>UpdatableRelationshipsEquals` |

- `BankAccountTestSamples` の `getBankAccountRandomSampleGenerator()` は、id に `AtomicLong` から採番した値を、文字列項目に `UUID.randomUUID().toString()` を使う。
- `AssertUtils` は、日時を UTC にそろえて比べる `zonedDateTimeSameInstant` と、`BigDecimal` を `compareTo` で比べる `bigDecimalCompareTo` を公開している。`<エンティティ>Asserts` はこれらを `usingComparator` で使う。

## 5. サービスの統合テスト

| クラス | クラスの注釈 | 特徴 |
|---|---|---|
| `service/UserServiceIT.java` | `@IntegrationTest`、`@Transactional` | `@MockitoBean` で `DateTimeProvider` を置き換え、監査の日時を固定する。`@AfterEach cleanupAndCheck` ですべてのキャッシュをクリアし、ユーザー件数が元に戻ったことを確認する |
| `service/MailServiceIT.java` | `@IntegrationTest`、`@ExtendWith(MockitoExtension.class)` | `@MockitoBean` で `JavaMailSender` を置き換え、`ArgumentCaptor` で送信内容を検証する |
| `security/DomainUserDetailsServiceIT.java` | `@Transactional`、`@IntegrationTest` | `@Qualifier("userDetailsService")` で対象を取り出す |

## 6. 単体テスト

単体テストは Spring のコンテキストを起動しない。

| クラス | 手法 |
|---|---|
| `config/WebConfigurerTest.java` | `MockEnvironment` と `MockServletContext` で対象を組み立て、`MockMvcBuilders.standaloneSetup(...)` でリクエストを送る。リクエストを受けるのは `config/WebConfigurerTestController.java` |
| `service/mapper/UserMapperTest.java` | 対象を `new` で作り、変換結果を AssertJ で検証する |
| `aop/logging/LoggingAspectTest.java` | `ProceedingJoinPoint` をモックにし、Logback の `ListAppender` で出力されたログを検証する |
| `security/SecurityUtilsUnitTest.java` | `SecurityContextHolder` に認証を設定して検証し、`@BeforeEach` と `@AfterEach` で `SecurityContextHolder.clearContext()` を呼ぶ |
| `management/SecurityMetersServiceTests.java` | `SimpleMeterRegistry` を渡してカウンタを検証する |
| `config/CRLFLogConverterTest.java` | `ILoggingEvent` をモックにして変換結果を検証する |
| `domain/*Test` | 4 節参照 |
| `TechnicalStructureTest` | ArchUnit で本体のクラスを解析する |

## 7. 認証を扱うテスト

| 方法 | 使うもの | 内容 |
|---|---|---|
| 認証済みにする | `@WithMockUser`、`@WithMockUser(authorities = ...)`、`@WithMockUser("<ログイン名>")` | 権限は文字列で指定する（`AuthorityResourceIT` は `"ROLE_ADMIN"`、`UserResourceIT` は `AuthoritiesConstants.ADMIN`） |
| 未認証にする | `@WithUnauthenticatedMockUser` | 空の `SecurityContext` を返す |
| JWT を実際に検証する | `@AuthenticationIntegrationTest` と `JwtAuthenticationTestUtils` | `security/jwt/TokenAuthenticationIT.java`、`security/jwt/TokenAuthenticationSecurityMetersIT.java` |

`AuthenticationIntegrationTest` は、読み込むクラスを `JHipsterProperties`、`WebConfigurer`、`SecurityConfiguration`、`SecurityJwtConfiguration`、`SecurityMetersService`、`AuthenticateController`、`JwtAuthenticationTestUtils` に限った合成注釈である。JWT の秘密鍵と有効期限は注釈の中で指定している。

`JwtAuthenticationTestUtils` が作れるトークンは次のとおりである。

| メソッド | トークンの性質 |
|---|---|
| `createValidToken(jwtKey)` | 有効。`anonymous` ユーザー、権限は `ROLE_ADMIN` |
| `createValidTokenForUser(jwtKey, user)` | 有効。ユーザー名を指定する |
| `createTokenWithDifferentSignature()` | 異なる鍵で署名している |
| `createExpiredToken(jwtKey)` | 有効期限が切れている |
| `createInvalidToken(jwtKey)` | 先頭を欠落させている |
| `createSignedInvalidJwt(jwtKey)` | JWT の形式ではない署名付きの文字列 |

## 8. テスト用の設定

| ファイル（`src/test/resources/` 基準） | 内容 |
|---|---|
| `config/application.yml` | プロファイル `test` の設定。テストに必要な設定を独自に定義する（`server.port: 10344`、`spring.liquibase.contexts: test`、JWT の設定など） |
| `config/application-testdev.yml` | インメモリの H2（`jdbc:h2:mem:jhipstersampleapplication:12344;...`）。Hibernate の第 2 レベルキャッシュを無効にする |
| `config/application-testprod.yml` | PostgreSQL 用。接続先は Testcontainers が差し込む |
| `META-INF/spring.factories` | `SqlTestContainersSpringContextCustomizerFactory` を `ContextCustomizerFactory` として登録する |
| `logback.xml` | テスト用のログ設定 |
| `junit-platform.properties` | タイムアウトとクラスの並び順 |
| `templates/mail/*.html`、`i18n/messages_en.properties` | テスト用のメールテンプレートとメッセージ |

- テスト用の `config/application.yml` は Maven のリソースフィルタリングの対象外である（`pom.xml` の `<resources>` は `src/main/resources/` だけを指定している）。動作するプロファイルは failsafe がシステムプロパティ `spring.profiles.active` で渡す。
- `testprod` のときは、`SqlTestContainersSpringContextCustomizerFactory` が `@EmbeddedSQL` の付いたテストクラスを検出し、`spring.datasource.url`、`spring.datasource.username`、`spring.datasource.password` にコンテナーの接続情報を設定する。コンテナーは `config/DatabaseTestcontainer.java`（`postgres:18.6`）が起動する。このクラスは Maven プロファイル `dev` ではテストのコンパイル対象から外れている（`pom.xml` の `testExcludes`）。
- `config/AsyncSyncConfiguration.java` は、`taskExecutor` を `SyncTaskExecutor` に差し替える。`@Async` の付いたメソッドがテストでは同期的に実行される。
- `junit-platform.properties` では、テストメソッド（`junit.jupiter.execution.timeout.testable.method.default`）のタイムアウトを 15 秒、`@BeforeAll` のメソッド（`junit.jupiter.execution.timeout.beforeall.method.default`）を 60 秒に設定している。
- クラスの並び順は `config/SpringBootTestClassOrderer.java` が決める。`@IntegrationTest` の付いたクラスを、そうでないクラスのあとに置く。

## 9. 負荷試験（Gatling）

- シミュレーションは `src/test/java/gatling/simulations/` に `BankAccountGatlingTest`、`LabelGatlingTest`、`OperationGatlingTest` の 3 つがある。いずれも `Simulation` を継承する。
- `BankAccountGatlingTest` は、`/api/account` への未認証のリクエスト（`401` を確認）、`/api/authenticate` によるログイン、`Authorization` ヘッダーを使った `/api/account` へのリクエスト（`200` を確認）、同じヘッダーを使った一覧取得・作成・取得・削除を順に実行する。
- システムプロパティ `baseURL`（既定値 `http://localhost:8080`）、`users`（既定値 100）、`ramp`（既定値 1）で接続先と負荷を変えられる。
- 実行に使う `gatling-maven-plugin` は `pom.xml` に `runMultipleSimulations` を `true` として定義されている。ライフサイクルのフェーズには結びついていないため、`./mvnw verify` では実行されない。設定は `src/test/gatling/conf/gatling.conf` にある。

## 10. テストを書くときの注意

| 注意点 | 内容 | 根拠 |
|---|---|---|
| クラス名の `IT` | クラス名に `IT` を含むと failsafe の対象になり、単体テストとしては実行されない | `pom.xml` の surefire と failsafe のパターン |
| タイムアウト | テストメソッドは 15 秒以内に終わらせる | `junit-platform.properties` |
| DB の後始末 | データを登録したら、`@Transactional` または `@AfterEach` で戻す。ユーザーを扱うテストはキャッシュもクリアする | `UserServiceIT#cleanupAndCheck` |
