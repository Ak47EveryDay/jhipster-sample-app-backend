# 主要処理フロー

> **位置づけ**：主なリクエストが、セキュリティフィルターからコントローラ、サービス、リポジトリまで、どのクラスを通って進むかをコードに沿って追ったものである。クラスごとの担当は `モジュール構成と共通部品.md`、エンドポイントの追加手順は `REST・エンティティ追加手順.md` を参照。
> パスは `src/main/java/io/github/jhipster/sample/` 基準、設定ファイルは `src/main/resources/` 基準で表記する。図に書いていない分岐（例外処理の細部など）はコードを参照すること。

---

## 1. 全体像

```
HTTP リクエスト
  │
  ▼
SecurityFilterChain（config/SecurityConfiguration#filterChain）
  ├ Bearer トークンの検証      oauth2ResourceServer().jwt()
  │     └ JwtDecoder          config/SecurityJwtConfiguration#jwtDecoder
  ├ パスごとの認可              authorizeHttpRequests(...)
  └ メソッド単位の認可          @PreAuthorize（@EnableMethodSecurity で有効）
  ▼
REST コントローラ（web/rest）
  │   ログ出力の AOP: aop/logging/LoggingAspect（dev のみ）
  ▼
サービス（service）または リポジトリ（repository）
  ▼
Hibernate → H2（dev）または PostgreSQL（prod）
  │
  ▼
コントローラ以降で送出された例外は web/rest/errors/ExceptionTranslator がエラー応答に変換する
```

| 関与する仕組み | 場所 | 役割 |
|---|---|---|
| CORS | `config/WebConfigurer#corsFilter` | `jhipster.cors` にオリジンの設定があるとき、`/api/**`、`/management/**`、`/v3/api-docs`、`/swagger-ui/**` に `CorsFilter` を適用する |
| セキュリティフィルターチェーン | `config/SecurityConfiguration#filterChain` | トークンの検証とパスごとの認可。CSRF は無効、セッションは使わない（`STATELESS`） |
| メソッドセキュリティ | `config/SecurityConfiguration` の `@EnableMethodSecurity(securedEnabled = true)` | `@PreAuthorize` を有効にする |
| トークンの検証と発行 | `config/SecurityJwtConfiguration` | `JwtDecoder` と `JwtEncoder` の Bean |
| 日時の形式 | `config/DateTimeFormatConfiguration` | 日時の変換を ISO 形式にそろえる |
| 遅延読み込みと JSON | `config/JacksonHibernateConfiguration` | Jackson 3 に Hibernate の遅延プロキシを認識させる |

## 2. ログイン（JWT の発行）

`POST /api/authenticate` は未認証で呼べる（`SecurityConfiguration` の `requestMatchers(HttpMethod.POST, "/api/authenticate").permitAll()`）。

```
POST /api/authenticate   { "username": "...", "password": "...", "rememberMe": false }
  │
  ▼
AuthenticateController.authorize(@Valid @RequestBody LoginVM)      web/rest/AuthenticateController.java
  │   new UsernamePasswordAuthenticationToken(username, password)
  ▼
authenticationManagerBuilder.getObject().authenticate(token)
  │
  ▼
DomainUserDetailsService.loadUserByUsername(login)                 security/DomainUserDetailsService.java
  │   email の形式なら findOneWithAuthoritiesByEmailIgnoreCase、それ以外は小文字にして findOneWithAuthoritiesByLogin
  │   見つからなければ UsernameNotFoundException
  │   有効化されていなければ UserNotActivatedException
  │   結果は DomainUserDetailsService.UserWithId（Spring Security の User に id を持たせたもの）
  ▼
パスワードの照合（PasswordEncoder は config/SecurityConfiguration#passwordEncoder の BCryptPasswordEncoder）
  │   失敗すれば BadCredentialsException（→ 401。5 節参照）
  ▼
SecurityContextHolder に認証を設定
  ▼
AuthenticateController.createToken(authentication, rememberMe)
  │   クレーム: sub = ログイン名、auth = 権限名（空白区切り）、userId = UserWithId の id、iat、exp
  │   有効期限: jhipster.security.authentication.jwt.token-validity-in-seconds
  │            （rememberMe が true なら token-validity-in-seconds-for-remember-me）
  │   署名: HS512（security/SecurityUtils.JWT_ALGORITHM）
  │   鍵: jhipster.security.authentication.jwt.base64-secret を Base64 デコードした値
  ▼
200 OK
   本体: { "id_token": "<token>" }
   ヘッダー: Authorization: Bearer <token>
```

| 確認箇所 | 内容 |
|---|---|
| `web/rest/vm/LoginVM.java` | `username` は `@NotNull` と `@Size(min = 1, max = 254)`、`password` は `@NotNull` と `@Size(min = 4, max = 100)` |
| `security/DomainUserDetailsService.java` | Bean 名は `userDetailsService`。`loadUserByUsername` に `@Transactional(readOnly = true)` を付ける |
| `web/rest/AuthenticateController.java` | `JWTToken` クラスの `idToken` に `@JsonProperty("id_token")` を付ける |
| `GET /api/authenticate` | 同じクラスの `isAuthenticated(Principal)`。認証されていれば `204`、そうでなければ `401` を返す |

## 3. 認証付きリクエスト

`GET /api/bank-accounts/{id}` を例にする。ヘッダー `Authorization: Bearer <token>` を付けて呼ぶ。

```
GET /api/bank-accounts/123
  │
  ▼
SecurityFilterChain
  ├ 1. トークンの検証
  │     JwtDecoder が署名と有効期限を検証し、Jwt を作る
  │     検証に失敗した場合は SecurityMetersService が失敗理由を数え、例外を送出する（10 節参照）
  ├ 2. 権限の設定
  │     Jwt の auth クレームから権限を取り出す
  │     （config/application.yml: authorities-claim-name: auth、authority-prefix: ''）
  └ 3. パスごとの認可
        /api/admin/**        → ROLE_ADMIN が必要
        /api/**              → 認証が必要（authenticated）
        このリクエストは「認証が必要」に該当
  ▼
BankAccountResource.getBankAccount(id)                           web/rest/BankAccountResource.java
  │   LOG.debug("REST request to get BankAccount : {}", id)
  │   クラス単位の @Transactional(rollbackFor = Exception.class) の中で実行
  ▼
BankAccountRepository.findOneWithEagerRelationships(id)
  │   default メソッド → findOneWithToOneRelationships(id)
  │   JPQL: left join fetch bankAccount.user（所有ユーザーを同じクエリで読む）
  ▼
ResponseUtil.wrapOrNotFound(Optional)  → 200 と JSON（結果が空なら 404）
```

| 確認箇所 | 内容 |
|---|---|
| `config/SecurityJwtConfiguration.java` | `jwtDecoder(SecurityMetersService)`。`NimbusJwtDecoder.withSecretKey(...).macAlgorithm(JWT_ALGORITHM)` |
| `config/application.yml` | `spring.security.oauth2.resourceserver.jwt` の `authority-prefix` と `authorities-claim-name` |
| `config/SecurityConfiguration.java` | パスごとのルール。`h2-console/**` の許可は dev のときだけ追加される |
| `config/SecurityConfiguration.java` | 認証・認可の失敗は `BearerTokenAuthenticationEntryPoint` と `BearerTokenAccessDeniedHandler` に任せる |
| テストソースの `config/ApiOnlyIT.java` | 未認証で `GET /index.html` は `401`。認証済み（`@WithMockUser`）で `GET /unmapped/path` は `403` |

- どのルールにも当てはまらないパスは拒否される。`README.md` に「未認証なら `401`、認証済みなら `403`」とある。
- 関連は遅延読み込みで、OSIV は無効である。コントローラがレスポンスを返す時点までに読み込みを終える必要があるため、リポジトリの `find...WithEagerRelationships` を使う（`repository/BankAccountRepository.java`）。

## 4. 作成・更新・削除の共通パターン

`POST /api/bank-accounts` を例にする。

```
POST /api/bank-accounts   { "name": "...", "balance": ... }
  │
  ▼  SecurityFilterChain（/api/** → 認証が必要）
BankAccountResource.createBankAccount(@Valid @RequestBody BankAccount)
  │   1. LOG.debug("REST request to save BankAccount : {}", bankAccount)
  │   2. id が null でなければ BadRequestAlertException(..., ENTITY_NAME, "idexists") → 400
  │   3. bankAccountRepository.save(bankAccount)
  │        主キーはシーケンス sequence_generator から採番
  ▼
ResponseEntity.created(new URI("/api/bank-accounts/" + id))
    .headers(HeaderUtil.createEntityCreationAlert(applicationName, true, ENTITY_NAME, id))
    .body(bankAccount)
  → 201 Created、Location ヘッダー、作成を知らせるアラートヘッダー
```

| 処理 | チェックの順序とエラーキー | 成功時 |
|---|---|---|
| 作成 | id がないこと（`idexists`） | `201` |
| 更新（PUT） | リクエストボディに id があること（`idnull`）→ パスとリクエストボディの id が一致すること（`idinvalid`）→ 対象が存在すること（`idnotfound`） | `200` |
| 部分更新（PATCH） | 更新と同じ。そのあと既存のエンティティに、null でない項目だけを設定する | `200` |
| 削除 | なし | `204` |

- エラーキーは `BadRequestAlertException` の第 3 引数で、エラー応答の `message` は `error.<エラーキー>` になる（`web/rest/errors/BadRequestAlertException.java`）。
- 更新・部分更新には成功時に `HeaderUtil.createEntityUpdateAlert`、削除には `HeaderUtil.createEntityDeletionAlert` を付ける。
- `BankAccountResource`、`LabelResource`、`OperationResource` は、コントローラのクラス単位で `@Transactional(rollbackFor = Exception.class)` を付けている。メソッドから例外が出ればロールバックされる。

## 5. エラーからエラー応答まで

### 5.1 例外の種類とレスポンス

| 発生元 | 例外 | 処理する箇所 | レスポンス |
|---|---|---|---|
| セキュリティフィルター（トークンがない・無効） | なし | `BearerTokenAuthenticationEntryPoint` | `401` |
| セキュリティフィルター（権限不足・どのルールにもないパス） | なし | `BearerTokenAccessDeniedHandler` | `403` |
| `@Valid @RequestBody` による入力チェック | `MethodArgumentNotValidException` | `ExceptionTranslator`（`ResponseEntityExceptionHandler` の処理を経由） | `400`、`fieldErrors` 付き |
| メソッド引数の制約違反 | `ConstraintViolationException` | `ExceptionTranslator#handleAnyException` | `400` |
| REST コントローラの入力チェック | `web.rest.errors.BadRequestAlertException` | `ExceptionTranslator#handleAnyException` | `400`、失敗を知らせるアラートヘッダー付き |
| サービスの業務例外 | `service.UsernameAlreadyUsedException` など | `ExceptionTranslator#getProblemDetailWithCause` が `web.rest.errors` 側の例外のレスポンスボディに差し替える | `400` |
| パスワードの長さ・照合の失敗 | `web.rest.errors.InvalidPasswordException` | `ExceptionTranslator#handleAnyException` | `400` |
| コントローラ内の認証・認可の例外 | `BadCredentialsException`、`AccessDeniedException` | `ExceptionTranslator#getMappedStatus` | `401`、`403` |
| ログイン（有効化されていないユーザー） | `security.UserNotActivatedException` | `ExceptionTranslator#toStatus` の既定の動作（ステータスを対応付ける規則はない） | `500`、`message` は `error.http.500` |
| 同時実行の失敗 | `ConcurrencyFailureException` | `ExceptionTranslator#getMappedStatus` | `409`、`message` は `error.concurrencyFailure` |
| Spring MVC の標準の例外（未対応の HTTP メソッドなど） | Spring MVC が送出する例外 | `ResponseEntityExceptionHandler` → `ExceptionTranslator#handleExceptionInternal` | `405` など、`message` は `error.http.<ステータス>` |
| `@ResponseStatus` の付いた例外 | `AccountResource` の内部クラス `AccountResourceException` など | `ExceptionTranslator#resolveResponseStatus` | 注釈に指定したステータスと理由 |
| 上記以外 | 任意の `RuntimeException` | `ExceptionTranslator#toStatus` の既定の動作 | `500`、`title` は `Internal Server Error` |

### 5.2 処理の流れ

```
REST コントローラ（またはサービス）で例外が送出される
  │
  ▼
ExceptionTranslator                                           web/rest/errors/ExceptionTranslator.java
  │
  ├ ResponseEntityExceptionHandler が処理する Spring MVC 標準の例外
  │     → handleExceptionInternal（レスポンスボディが null なら wrapAndCustomizeProblem で作る）
  └ それ以外の例外
        → handleAnyException
  │
  ▼
wrapAndCustomizeProblem
  ├ getProblemDetailWithCause   レスポンスの元を作る
  │     ・service の 3 種類の業務例外 → web.rest.errors 側の例外のレスポンスボディ
  │     ・ErrorResponseException（BadRequestAlertException など）→ それ自身のレスポンスボディ
  │     ・その他 → ステータスだけを持つ空のレスポンスボディ
  └ customizeProblem           レスポンスボディの各項目をそろえる
        type, title, detail, message, path, fieldErrors
  │
  ▼
handleExceptionInternal → application/problem+json のレスポンス
```

### 5.3 レスポンスボディの項目

| 項目 | 内容 | 設定箇所 |
|---|---|---|
| `type` | エラーの種類を表す URI。入力チェックエラーは `ErrorConstants.CONSTRAINT_VIOLATION_TYPE`、それ以外は `ErrorConstants.DEFAULT_TYPE` | `ExceptionTranslator#getMappedType`、`web/rest/errors/ErrorConstants.java` |
| `title` | HTTP ステータスの理由句。`@ResponseStatus` の `reason` や、入力チェックエラーの `Method argument not valid` が優先される | `ExceptionTranslator#extractTitle` |
| `status` | HTTP ステータス | `ExceptionTranslator#toStatus` |
| `detail` | 例外のメッセージ | `ExceptionTranslator#getCustomizedErrorDetails` |
| `message` | メッセージのキー。入力チェックエラーは `error.validation`、同時実行の失敗は `error.concurrencyFailure`、`BadRequestAlertException` は `error.<エラーキー>`、それ以外は `error.http.<ステータス>` | `ExceptionTranslator#customizeProblem`、`#getMappedMessageKey` |
| `path` | リクエストの URI | `ExceptionTranslator#customizeProblem` |
| `fieldErrors` | `@Valid @RequestBody` の入力チェックエラーの一覧。各要素は `objectName`、`field`、`message`。`objectName` は末尾の `DTO` を取り除いた名前 | `ExceptionTranslator#getFieldErrors`、`web/rest/errors/FieldErrorVM.java` |
| `params` | `BadRequestAlertException` の `entityName` | `web/rest/errors/BadRequestAlertException.java` |

- `detail` は、prod プロファイルで動いているときは、内部情報を隠すために置き換えられる。`HttpMessageConversionException` は `Unable to convert http message`、`DataAccessException` は `Failure during data access`、メッセージにパッケージ名が含まれる場合は `Unexpected runtime exception` になる（`ExceptionTranslator#getCustomizedErrorDetails`、`#containsPackageName`）。
- エラー応答に原因の連鎖は含めない（`ExceptionTranslator` の `CAUSAL_CHAIN_ENABLED = false`）。
- `BadRequestAlertException` のときは、`ExceptionTranslator#buildHeaders` が `HeaderUtil.createFailureAlert(...)` で失敗を知らせるアラートヘッダーを追加する。
- `spring.mvc.problemdetails.enabled: true` が `config/application.yml` で設定されている。
- テストソースの `web/rest/errors/ExceptionTranslatorIT.java` が、各ケースのステータスとレスポンスボディを検証している。テスト用の例外を投げるコントローラは `web/rest/errors/ExceptionTranslatorTestController.java` である。

## 6. ユーザーの検索とキャッシュ

- `UserRepository.findOneWithAuthoritiesByLogin` と `findOneWithAuthoritiesByEmailIgnoreCase` には `@Cacheable` が付いている。キャッシュ名は `UserRepository.USERS_BY_LOGIN_CACHE`（`usersByLogin`）と `UserRepository.USERS_BY_EMAIL_CACHE`（`usersByEmail`）で、結果が null のときはキャッシュしない（`unless = "#result == null"`）。
- キャッシュの領域は `config/CacheConfiguration.java` の `cacheManagerCustomizer` が作る。保持時間と最大件数は `jhipster.cache.ehcache.time-to-live-seconds` と `jhipster.cache.ehcache.max-entries` による。
- ユーザーを変更したあとは `UserService#clearUserCaches` がログイン名と email の両方のキャッシュを破棄する。`UserService` の各更新メソッドがこれを呼んでいる。

## 7. 監査項目の設定

`AbstractAuditingEntity` を継承したエンティティには、保存時に次の 4 項目が自動で設定される。

| 項目 | 注釈 | カラム | 値の設定元 |
|---|---|---|---|
| 作成者 | `@CreatedBy` | `created_by` | `SpringSecurityAuditorAware#getCurrentAuditor` |
| 作成日時 | `@CreatedDate` | `created_date` | フレームワーク（初期値は `Instant.now()`） |
| 更新者 | `@LastModifiedBy` | `last_modified_by` | `SpringSecurityAuditorAware#getCurrentAuditor` |
| 更新日時 | `@LastModifiedDate` | `last_modified_date` | フレームワーク（初期値は `Instant.now()`） |

- 有効にしているのは `config/DatabaseConfiguration.java` の `@EnableJpaAuditing(auditorAwareRef = "springSecurityAuditorAware")` と、`domain/AbstractAuditingEntity.java` の `@EntityListeners(AuditingEntityListener.class)` である。
- `security/SpringSecurityAuditorAware.java#getCurrentAuditor` は、現在のユーザーのログイン名（`SecurityUtils.getCurrentUserLogin()`）を返し、取得できなければ `Constants.SYSTEM`（`system`）を返す。
- 現状この基底クラスを継承しているのは `User` のみである。`BankAccount`、`Label`、`Operation` に監査項目はない。

```
AccountResource.registerAccount   などから呼ばれる
  │
  ▼
MailService.sendActivationEmail(user)        @Async（service/MailService.java）
  │   非同期実行: AsyncConfiguration が定義した taskExecutor
  │   テスト（testdev・testprod）では AsyncSyncConfiguration が同期実行に差し替える
```

| メール | メソッド | テンプレート | 件名のキー | リンク先 |
|---|---|---|---|---|
| アカウント有効化 | `sendActivationEmail` | `mail/activationEmail` | `email.activation.title` | `${baseUrl}/account/activate?key=...`（`activationKey`） |

## 9. 起動時のマイグレーション

```
アプリの起動
  │
  ▼
LiquibaseConfiguration.liquibase(...)                 config/LiquibaseConfiguration.java
  │   application.liquibase.async-start が true（既定値）なら非同期で SpringLiquibase を作る
  │   false なら同期で作る
  │   チェンジログ: classpath:config/liquibase/master.xml
  │   コンテキスト: spring.liquibase.contexts（dev は dev, faker、prod は prod、test は test）
  │   no-liquibase プロファイルなら setShouldRun(false)
  ▼
master.xml が changelog/ 配下の XML を順に include する
  ├ 00000000000000_initial_schema.xml      シーケンス、jhi_user などの JHipster のコアテーブル、初期データ
  ├ 20150805124838_added_entity_BankAccount.xml
  ├ 20150805124936_added_entity_Label.xml
  ├ 20150805125054_added_entity_Operation.xml
  ├ 20150805124838_added_entity_constraints_BankAccount.xml
  └ 20150805125054_added_entity_constraints_Operation.xml
```

- `application.liquibase.async-start` の既定値は `config/ApplicationProperties.java` の `Liquibase` クラスで `true` に定義されている。

- チェンジログの形式と追加のしかたは `REST・エンティティ追加手順.md` を参照。

## 10. トークン検証失敗のメトリクス

`SecurityJwtConfiguration#jwtDecoder` は、トークンの検証で例外を受け取ったとき、例外のメッセージに含まれる文言によって `management/SecurityMetersService.java` のメソッドを呼び、そのあと例外をそのまま送出する。

| 例外メッセージに含まれる文言 | 呼ぶメソッド | メトリクスの `cause` タグ |
|---|---|---|
| `Invalid signature` | `trackTokenInvalidSignature()` | `invalid-signature` |
| `Jwt expired at` | `trackTokenExpired()` | `expired` |
| `Invalid JWT serialization`、`Malformed token`、`Invalid unsecured/JWS/JWE` | `trackTokenMalformed()` | `malformed` |
| 上記以外 | `LOG.error("Unknown JWT error {}", ...)` | なし |

メトリクスの名前は `SecurityMetersService.INVALID_TOKENS_METER_NAME`（`security.authentication.invalid-tokens`）である。テストソースの `security/jwt/TokenAuthenticationSecurityMetersIT.java` がカウンタの増加を検証している。
